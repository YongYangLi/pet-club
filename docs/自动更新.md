# 自动更新（腾讯云 COS）

客户端会自己去 COS 上问一句「有新版本吗」，有就悄悄下下来；
**下次启动时**自动换上；在**托盘图标的菜单**里点「检查更新」，下完会**自己重启换上**
（不用再点第二次）。代码在 `petclub/update.py`，发版工具是 `tools/make_release.py`。

---

## 1. 它是怎么工作的

```
客户端启动
   │
   ├─ 上次下好了 .new？ ──有──▶ 起一个 .bat：等本进程退出 → 摘只读位 → move 覆盖 exe
   │                          → 重新拉起（然后本进程直接退出，不建窗口）
   │
   └─ 没有 → 正常启动
              └─ 4 秒后（后台线程）GET latest.json
                    ├─ 版本不比我新 → 什么都不做，3 小时后再看
                    └─ 比我新 → 下载到 pet-club.exe.new → 校验大小 + sha256
                                  ├─ 后台自己发现的：冒泡「新版 x.y.z 已就绪」
                                  │                托盘菜单里出现「更新到 x.y.z · 重启」
                                  └─ 用户手动点的：冒泡「正在重启换上」，1.5 秒后自己换掉
```

三个关键设计：

**① 为什么换文件要等进程退出**
Windows 对正在运行的 exe 加了写锁，`MoveFileEx` 也绕不过去 —— 程序自己换不掉自己。
所以 `pet-club.exe.new` 只是下好放在那儿，真正的 `move` 由一个 detach 的 `.bat`
在进程消失后做：先用 `tasklist /FI "PID eq <自己>"` 确认老进程没了，再 `attrib -r`
摘掉只读位，然后 `move /y`，成功后把新 exe 拉起来。

这里有两个踩过的坑，改动都在 `update.py` 的常量注释里：

| 坑 | 症状 | 修法 |
|---|---|---|
| 目标 exe 带只读位（从浏览器/压缩包出来的文件常有） | `move /y` 直接「拒绝访问」，重试多少次都换不上 —— `.new` 下好了、老 exe 一个字节没变 | 换之前 `attrib -r`，Python 侧还先 `os.chmod` 试一次 |
| `DETACHED_PROCESS \| CREATE_NO_WINDOW` 一起传 | 后者被 Windows 忽略，cmd 自己分配控制台 → 屏幕角落弹出一个黑窗在里面 `ping 127.0.0.1` | 只留 `CREATE_NO_WINDOW`（`tools/probe_update.py` 验的就是这个） |
| 拉起新版本时继承了老进程的 PyInstaller 启动器变量 | 新 exe 以为自己已解包，去已删除的老临时目录加载 `python3xx.dll` → 弹「Failed to load Python DLL」，可文件其实换好了 | 起脚本时传干净环境（`update._clean_env()`），脚本里再补一遍 `set "变量="`；`tools/probe_relaunch.py` 验的就是这个（详见 5.1） |

换不上时脚本会往 `%TEMP%\pet-club-update.log` 写一行原因，不再只是「什么也没发生」。
另外 `.new` 必须**比当前版本新**才会被换上，否则「手工拷了新 exe、旁边躺着旧 .new」
会在启动时把自己降级回去。

`move` 只搬 `.new`，它的附注 `.new.json` 会独自留在原地，所以换成功后脚本顺手 `del` 掉，
启动时的 `cleanup()` 也会清掉「有 json 没 .new」的空壳 —— 否则每更新一次，exe 旁边就多一个垃圾。

**② 为什么先传 exe、最后传清单**
`latest.json` 是开关：它在，所有客户端**同时**看到新版本；它不在，谁也看不到。
先传清单后传 exe 的话，中间那几分钟客户端会去拉一个还不存在的地址，
然后报「下载失败」—— 明明什么都没坏，却像坏了。

**③ 为什么校验 sha256**
下到一半断网、COS 返回了一个错误页、杀软动了手脚 —— 这几种「看起来下完了」的
文件如果被换上，客户端就再也起不来了。校验不过当场删掉 `.part`，
`.new` 这个文件名本身就等于「下好了且校验过」。

## 2. 一次性配置（只做一次）

### 2.1 建桶

腾讯云控制台 → 对象存储 → 新建存储桶：

| 项 | 值 |
|---|---|
| 名称 | 随便，比如 `pet-club-1300000000` |
| 地域 | 离你近的，比如 `ap-beijing` |
| 访问权限 | **公有读私有写** |
| 版本控制 | 建议开（发错了能退回去） |

### 2.2 建目录并上传一次

在桶里建一个目录 `pet-club/`，里面放两个东西：

```
pet-club/
├── latest.json     ← 清单，客户端只认它（版本号在这，它是「开关」）
└── pet-club.exe    ← exe，名字固定，不带版本号；每次发版覆盖它
```

**文件名不带版本号**是故意的：地址始终不变，改清单里的 `version` 就等于发版。
带版本号的话每发一版都要换地址、桶里越堆越多，而「哪个才是当前版本」这件事
清单里本来就写着。代价是回退不再等于「把旧文件名改回去」，得用旧代码重打一次
再覆盖 —— 所以发版前确认 `dist/pet-club.exe` 是刚打出来的那个。

### 2.3 把地址填进客户端

`petclub/config.py`：

```python
VERSION = '1.2.2'
UPDATE_URL = ('https://dev-cos-1259275319.cos.ap-shanghai.myqcloud.com'
              '/pet-club/latest.json')
```

> **桶名在域名里，路径里不要再写一遍。** COS 的对象地址形状是
> `https://<桶名>.cos.<地域>.myqcloud.com/<目录>/<文件>`，
> 所以正确写法是 `…/pet-club/latest.json`，不是 `…/<桶名>/pet-club/latest.json`。
> 多写那一段的后果是客户端一路 404，而控制台上看着一切正常 —— 真踩过，见 §5。

`UPDATE_URL` 留空 = 关掉自动更新（源码模式、内网环境就是这个状态）。

> 地址必须是 **公网可访问的 HTTPS**：客户端只是普通 GET，不带签名。
> 桶开了「公有读」就行，不需要 CDN，也不需要 CORS（不是浏览器在请求）。

## 3. 每次发版

```bash
# 1) 改版本号（唯一来源）
#    petclub/config.py  →  VERSION = '1.2.3'

# 2) 打包 + 生成清单
py tools/make_release.py ^
   --base https://dev-cos-1259275319.cos.ap-shanghai.myqcloud.com/pet-club ^
   --note "新增：托盘图标、Ctrl+V 粘贴、表情包「他人」分组"

# 3) 上传（顺序不能反）
coscli cp dist/pet-club.exe cos://<桶>/pet-club/pet-club.exe
coscli cp dist/latest.json  cos://<桶>/pet-club/latest.json
```

`latest.json` 长这样：

```json
{
  "version": "1.2.2",
  "url": "https://.../pet-club/pet-club.exe",
  "size": 24119282,
  "sha256": "672a…",
  "note": "修复：更新地址多写了一层桶名导致 404",
  "date": "2026-11-10 16:52"
}
```

`url` 也可以写相对路径（`pet-club.exe`），客户端会按清单地址补全。
`size` 和 `sha256` 是**下载后的验收标准**，对不上就删掉重下 —— 它们同时兜住了
「地址覆盖了但 CDN/浏览器缓存还是旧的」这一类问题。

## 4. 用户那边看到什么

| 状态 | 界面上 |
|---|---|
| 有新版，正在下 | 无感（后台线程，不挡任何操作） |
| 下好了（后台自己发现的） | 桌宠冒一句「新版 1.3.1 已就绪，右键「更新到 1.3.1」就能换上」 |
| 下好了（用户点的「检查更新」） | 冒一句「新版 1.3.1 下载好了，正在重启换上」，1.5 秒后自己换掉 |
| 托盘菜单 / 左键面板 | 多一行「更新到 1.3.1 · 重启」，点它就换 |
| 用户什么都不点 | 关掉再开，`run.py` 在开窗口之前就把 `.new` 换上并自动重启 |
| 已经最新 / 检查失败 | 什么都不说（自动检查时）。手动点「检查更新」才回话 |

**不会**弹对话框、**不会**打断正在打的字。后台自己发现的更新**不会**擅自重启
（可能正有人打字），必须等用户点；**只有用户主动点了「检查更新」，才算说过「我要装」，
下完直接重启**。

## 5. 排错

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 托盘里那一行是灰的「检查更新 · 未配置」 | `UPDATE_URL` 是空的，或者跑的是源码（没打包） | 填地址 / 用 exe |
| 一直提示「拉不到清单」 | 桶没开公有读，或地址写错 | 浏览器直接打开那个 URL，能下载 JSON 就对了 |
| 提示「拉不到清单：HTTP 404」 | 地址多写了一段，通常是路径里又重复了一遍桶名 | 桶名只出现在域名里，路径不该有它 |
| 下载完提示「校验不一致」 | 上传的 exe 和清单不是同一次生成的（覆盖了 exe 没换清单，或反过来） | 重新跑 `make_release.py`，两个一起传 |
| 换上之后起不来 | 八成是杀软把 `.new` 当可疑文件锁了 | 关掉自动更新，手动发一次 |
| 同一版本反复提示更新 | `config.VERSION` 和 `latest.json` 的 version 不一致 | 版本号只有一个来源，别手写第二份 |
| 点了更新、程序关了却还是老版本，旁边躺着 `pet-club.exe.new` | 换文件失败。看 `%TEMP%\pet-club-update.log`：`换不上：move 反复失败` = 只读位摘不掉/被占用；`等不到老进程退出` = 有实例没退干净 | 1.3.1 起会自动摘只读位；手工救急：`attrib -r pet-club.exe` 后把 `.new` 改名覆盖 |
| 更新时屏幕角落闪出一个黑窗在 ping 127.0.0.1 | 1.3.1 之前把 `DETACHED_PROCESS` 和 `CREATE_NO_WINDOW` 一起传了，后者被忽略 | 升级到 1.3.1 |
| 更新时弹「Failed to load Python DLL '...\\_MEI...\\python3xx.dll' / LoadLibrary: 找不到指定的模块」，可桌面上的 exe 明明是新版、双击又能正常开 | 1.3.3 及以前：更新脚本是老进程的子进程，继承了 bootloader 留下的 `_PYI_APPLICATION_HOME_DIR` / `_PYI_ARCHIVE_FILE` / `_PYI_PARENT_PROCESS_LEVEL`。新 exe 三个变量齐全 → 跳过解包，直接去**老进程那个已经删掉的**临时目录里加载 python DLL | 升级到 1.3.4（起脚本时环境已清干净，脚本里也补了一遍 `set "变量="`）。已经被弹到的话点「确定」，再双击桌面的 exe 即可 |

### 5.1 「Failed to load Python DLL」到底怎么回事

单文件 exe 的 bootloader 会先把自己解包到 `%TEMP%\_MEIxxxx`，再拉起真正的子进程，
并用这三个环境变量告诉子进程「别解包了，东西在这儿」。它们是给子进程看的，
可我们的更新脚本同样跑在这个进程树里 —— cmd 和 `start` 会原样继承。

于是新 exe 一启动就发现「我已经被解包过了」，直接去 `_PYI_APPLICATION_HOME_DIR`
里 `LoadLibrary("python315.dll")`。那个目录属于**刚刚退出的老进程**，已经跟着
一起删了，所以只会得到「找不到指定的模块」。

这也解释了为什么症状这么怪：**文件其实早换好了**（`move` 在拉起之前就成功了），
双击（Explorer 起，环境干净）一切正常，只有「自动重启」这一下是坏的；
而坏掉的进程没走到 `run.py`，所以 `cleanup()` 也没机会删掉旁边的
`pet-club.exe.new.json`。

`tools/probe_relaunch.py` 把这条链路原样跑一遍：拷一份 exe 当老版本、再拷一份
当 `.new`、用 `_script()` 生成真脚本、**带着假的启动器变量**去 `cmd /c`，
最后要求「没弹 DLL 报错」且「新进程自己解包出了新目录」。

看日志：`dist` 版是 `--windowed`，没有控制台；临时排查用源码跑
`py run.py`，`update.py` 的所有失败都会打一行 `print`。
换文件那一段是批处理在跑，它的记录在 `%TEMP%\pet-club-update.log`。

## 6. 没做的事情（有意）

- **不做增量更新**：整包 20MB，几十个人用，没必要为省 15MB 引入 bsdiff。
- **不做强制更新**：老版本客户端仍然能用（协议向后兼容），只是看不到新功能。
- **不做灰度**：一个桶一份清单，所有人都一样。要灰度就多建几个桶、把地址写进不同渠道的包。
- **不自动重启正在用的用户**：后台检查只下载不安装；换文件只在「启动时」和
  「用户主动点了检查更新 / 更新到 x.y.z」这几个时刻发生。
